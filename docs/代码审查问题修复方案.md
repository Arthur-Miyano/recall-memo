# 代码审查问题修复方案

> 基线：`dd3a45f` 及其后的当前工作区  
> 适用范围：本地、单用户、单进程、单 worker 版本  
> 文档目的：把代码审查结论转化为可实施、可测试、可回滚的修复任务。

## 1. 结论与原则

当前项目的主要风险集中在会话操作的正确性、LLM 失败恢复、导入资源边界和自动化质量门禁。全面 DDD 化、全部接口版本化、全项目 TypeScript 化等建议有长期价值，但不应先于数据正确性修复。

实施时遵循以下原则：

1. 当前仍以本地单用户产品为目标，不提前引入分布式任务系统和多租户架构。
2. 数据库事务不得跨越 LLM 或文件解析等长时间操作。
3. 同一业务事实只保留一个权威来源；缓存和快照必须能够从权威数据重建。
4. 优先建立高杠杆的深模块接口，避免为每张表建立只有简单 CRUD 的浅 Repository。
5. 每项修复必须同时补充行为测试，覆盖失败路径和重复请求，而不只检查代码是否被调用。

## 2. 修复范围与优先级

| 阶段 | 工作包 | 目标 |
|---|---|---|
| P0 | 会话幂等与操作恢复 | 防止重复答题、重复推进和中间状态卡死 |
| P0 | LLM 错误边界 | 正确分类故障切换，避免泄露内部异常 |
| P0 | 导入安全与资源限制 | 防止畸形文件、超大文件和无界 LLM 消耗 |
| P1 | 状态与数据库基础 | 集中状态定义，引入迁移版本、约束和 SQLite 参数 |
| P1 | CI 与关键测试 | 让默认测试命令可复现，覆盖前后端关键用户旅程 |
| P1 | 前端恢复和数据状态 | 刷新后恢复会话，明确区分真实数据与演示数据 |
| P2 | 定向结构优化 | 缩小 Orchestrator 和大型 Vue 文件的变化范围 |
| P2 | 产品与可观测性 | 增加评分说明、操作审计、请求追踪和撤销能力 |

## 3. P0：会话幂等与操作恢复

### 3.1 当前问题

`backend/agents/orchestrator.py` 在读取会话状态后调用 LLM，最后才写记录并推进 `current_index`。双击提交、网络重试或两个标签页并发操作时，多个请求可能同时通过状态检查，导致：

- 同一题生成多条答题记录；
- 会话进度推进两次；
- 统计和待补答队列重复更新；
- LLM 成功但最终写库失败后无法安全重试；
- 服务中断后会话停留在评分或出题中状态。

### 3.2 数据模型

新增 `workflow_operations` 表：

| 字段 | 说明 |
|---|---|
| `id` | 服务端操作 ID |
| `idempotency_key` | 客户端生成的幂等键，唯一索引 |
| `session_id` | 所属会话 |
| `question_id` | 当前题目 |
| `question_index` | 提交时的会话题目序号 |
| `operation_type` | `answer`、`skip`、`generate_question`、`review` |
| `status` | `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED` |
| `result` | 已成功操作的最小响应快照 |
| `error_code` | 稳定的失败分类 |
| `retry_count` | 已重试次数 |
| `created_at` / `updated_at` | UTC 时间 |

在 `sessions` 增加 `version` 整数字段。答题记录增加 `operation_id` 唯一约束，并按需要增加 `(session_id, question_index, attempt_kind)` 联合唯一约束。

不要使用简单的 `(session_id, question_id)` 唯一约束，因为面试编排允许同一道题在同一会话重复出现。

### 3.3 执行流程

1. 前端在一次提交开始时生成 `idempotency_key`，失败重试必须复用同一个键。
2. 短事务读取会话，并以 `WHERE id = ? AND version = ? AND state = ?` 条件更新版本与操作状态。
3. 条件更新失败时重新读取：
   - 同幂等键已成功：直接返回已保存结果；
   - 同题操作正在进行：返回 `OPERATION_IN_PROGRESS`；
   - 会话已经推进：返回 `ANSWER_ALREADY_SUBMITTED`。
4. 提交短事务，不持有数据库事务调用 LLM。
5. LLM 成功后开启新事务，原子写入记录、待补答队列、统计、会话结果与下一状态。
6. LLM 或写库失败时把操作标记为 `FAILED`，保留可安全重试的信息。

操作状态与会话业务状态应分开管理。`SCORING_FAILED`、`IMPORT_FAILED` 等不应全部塞进同一个 `SessionState` 枚举。

### 3.4 验收测试

- 两个并发请求使用相同幂等键，只产生一条记录和一次进度推进。
- 两个不同幂等键同时提交同一题，只有一个成功，另一个返回稳定错误码。
- LLM 超时后可以重试，且不会重复计入答题统计。
- LLM 成功、最终事务失败后，再次提交能够安全完成。
- 服务在 `RUNNING` 操作期间重启后，恢复接口返回可重试状态。
- 跳过和回答并发时只能有一个操作生效。

## 4. P0：LLM 错误边界

### 4.1 异常分类

建立统一异常类型：

- `LLMTimeoutError`：允许有限重试或切换；
- `LLMRateLimitError`：允许退避后切换；
- `LLMTemporaryError`：网络失败和 Provider 5xx；
- `LLMAuthenticationError`：不切换，提示检查配置；
- `LLMRequestError`：Prompt 过长、模型不存在、参数或 Schema 错误，不切换；
- `LLMOutputValidationError`：输出无法解析或未通过约束，可进行一次受控重试。

禁止继续使用“捕获所有 `Exception` 后自动切换 Provider”的规则。单 Provider 初始建议最多重试 1 次，总调用必须受统一截止时间约束。

### 4.2 对外错误

API 只返回稳定结构，例如：

```json
{
  "error": {
    "code": "LLM_PROVIDER_UNAVAILABLE",
    "message": "模型服务暂不可用，请检查模型配置或稍后重试"
  },
  "request_id": "..."
}
```

Provider 原始响应、内部 URL、请求头、Prompt、文档内容和完整异常只允许进入脱敏日志。数据库导入失败也不得向前端返回本地备份绝对路径和原始异常文本。

### 4.3 输出校验

评分结果、导入题目和助理动作分别建立 Pydantic 输出模型，限制字段、长度和分值范围。支持原生 Structured Output 的 Provider 优先使用原生能力；其他 Provider 继续使用文本 JSON，但必须经过相同模型校验。

## 5. P0：导入安全与资源限制

### 5.1 统一上传策略

所有上传入口复用一个上传策略模块，不允许各 API 自行读取文件。初始默认值建议配置化：

- 单文件最大 20 MiB；
- 单批最多 10 个文件；
- 单次总上传最大 50 MiB；
- PDF 最多 300 页；
- 提取文本最多 2,000,000 字符；
- 单任务最大题目数、LLM 请求数、Token 预算和总运行时间均设上限。

读取上传内容时按块累计大小，超过限制立即终止，不再使用无界 `await file.read()`。

扩展名白名单保留 `.pdf`、`.md`、`.txt`、`.json`、`.db`。MIME 只作为辅助判断，最终仍以文件签名和实际解析结果为准。当前功能不接受压缩包，因此无需实现压缩炸弹解析逻辑，只需明确拒绝压缩格式。

### 5.2 数据库合并导入

当前功能语义是“把旧库合并进当前库”，继续保留单事务合并和导入前备份，不改成整库替换。合并前增加：

1. 文件大小和 SQLite magic 校验；
2. `PRAGMA quick_check`，必要时执行 `integrity_check`；
3. 读取 `schema_version`；
4. 校验允许的表名和必需列；
5. 拒绝未知 trigger、view 和虚拟表；
6. 限制每张表最大行数及文本/JSON 字段长度；
7. 对 mode、state、分数、日期和外键引用做确定性校验；
8. 完整校验通过后才创建备份并开始合并。

验收时覆盖损坏 SQLite、伪造文件头、未知 schema、恶意 trigger、超大表、缺列、非法 JSON、导入中异常回滚和重复导入幂等。

## 6. P1：状态与数据库基础

### 6.1 状态定义

把 `SessionState` 和终态集合移入不依赖 FastAPI、数据库和 Agent 的独立模块，例如 `domain/session_state.py`。Orchestrator、启动清理、API 和测试全部引用同一份定义。

### 6.2 正式迁移

增加最小 `schema_version` 机制，每个迁移具备唯一版本、事务边界和从旧版本升级的测试。项目进一步扩张后再评估 Alembic；不要求为了当前几次 SQLite 迁移立即引入完整迁移框架。

`backfill_retry_queue()` 改成一次性版本迁移，并使用 SQL 查询每题最新记录，避免每次启动全表扫描和 Python 内存聚合。

### 6.3 约束与 SQLite 参数

- 为 `Record`、`RetryQueueItem`、`QuestionFocus` 等补齐真实外键；
- 添加分数范围、mode/state 合法值和必要唯一约束；
- 连接建立时执行 `PRAGMA foreign_keys = ON`；
- 评估启用 WAL、`busy_timeout = 5000` 和 `synchronous = NORMAL`；
- 删除、迁移和导入测试必须验证不存在孤儿记录。

启用约束前先提供存量数据检查脚本，发现非法数据时停止迁移并给出可恢复提示。

## 7. P1：CI 与测试

### 7.1 修复默认测试命令

从 `backend/pytest.ini` 删除固定的 `--basetemp=.pytest-tmp`。个人机器的临时目录 ACL 问题放到本地说明或个人配置中处理，不进入仓库默认配置。

同时修复测试结束后的 SQLAlchemy engine/SQLite 连接释放。当前测试虽然通过，但仍有大量 `ResourceWarning: unclosed database`。

### 7.2 GitHub Actions

建立最小 CI：

```text
backend: 安装锁定依赖 → pytest + coverage gate → Ruff
frontend: npm ci → npm test → npm run build
```

后续引入 TypeScript、Vitest 组件测试后，再加入 `vue-tsc` 和组件覆盖率门禁。安全扫描可以独立执行，不阻塞第一版 CI 落地。

### 7.3 测试优先级

优先新增：

1. 会话重复提交和并发提交；
2. LLM 超时、4xx、429、5xx 和错误脱敏；
3. 操作失败与服务重启恢复；
4. 上传大小、页数、Token 预算与数据库 schema 校验；
5. Vue 会话恢复、offline/demo 切换和重复点击；
6. 一条完整 E2E：导入题目 → 训练 → 答错 → 待补答 → 再训练 → 查看统计。

后端行覆盖率继续保持不低于 90%，同时对核心状态分支建立显式行为断言。覆盖率不能替代并发和失败路径测试。

## 8. P1：前端恢复与数据状态

### 8.1 会话恢复

扩展现有 Pinia `session` store，不重复建立多套状态容器：

- 保存当前服务端 `session_id`、未提交草稿、最后同步时间和本地快照版本；
- 进入训练/面试页时先查询服务端状态，不再无条件创建新会话；
- 服务端状态是唯一事实来源，本地只恢复尚未提交的输入草稿；
- 服务端已完成而前端未收到响应时，根据 operation 结果恢复，不重新提交；
- 明确处理会话过期、服务端不存在和本地快照冲突。

### 8.2 真实数据与演示数据

页面统一使用 `loading`、`online`、`demo/offline` 三种显式状态。演示数据必须持续显示明显标识，并禁止执行会被误认为已持久化的操作。后端恢复后重新加载真实数据，不能把 mock 快照继续当成用户数据。

### 8.3 API 客户端

增强现有 `frontend/src/api/index.js`，不新建第三套封装：

- 统一 `ApiError` 和机器错误码；
- 支持超时和 `AbortController`；
- 页面卸载时取消无用请求；
- 兼容 204 和文件下载；
- 幂等操作传递 `idempotency_key`；
- 仅对明确可重试的 GET 或幂等请求自动重试。

## 9. P2：定向结构优化

### 9.1 后端

保留 `OrchestratorAgent.run(action, ...)` 作为小型外部接口，内部优先提取两个高杠杆模块：

- `SessionWorkflow`：状态规则、合法转换、恢复决策；
- `OperationCoordinator`：版本检查、幂等、短事务和操作结果持久化。

Agent 只负责需要 LLM 推理的任务。数据库访问先集中到上述工作流的少量查询接口；只有出现第二种持久化实现或大量重复查询时，再引入 Repository。不要为每张表建立只有 `get/save/delete` 的浅包装。

`backend/api/datamove.py` 可进一步拆出数据库校验器和合并器；HTTP 文件只保留参数转换和错误映射。

### 9.2 前端

按独立变化原因拆分，而不是按文件行数拆分：

- `DashboardView.vue`：提取数据加载、图表数据映射和独立弹层；
- `InkCrab.vue`：提取聊天会话、动作确认和拖拽尺寸逻辑；
- `BankOverview.vue`：提取编辑/迁移工作流；
- `MemorizeFlow.vue`：提取会话恢复与题目推进逻辑。

TypeScript 从 API DTO、会话状态和导入任务开始渐进迁移。完成 CI 和组件测试前，不进行一次性全项目转换。

## 10. 本地安全边界

官方启动方式继续强制绑定 `127.0.0.1`。设置、数据库导入导出、删除和批量迁移接口至少增加：

- Host 与 Origin 校验；
- 启动时生成的本地随机令牌，或同等强度的本地请求保护；
- `.env` 原子写入和同进程写锁；
- API Key 全量脱敏；
- CSP、`nosniff`、Referrer-Policy 和禁止 iframe 嵌入等基础响应头。

如果未来允许监听 `0.0.0.0`、云端部署或多用户访问，本节必须升级为发布阻断条件，并增加认证、授权、用户数据隔离、CSRF 防护和审计日志。

## 11. 产品与可观测性

- 评分页明确显示“AI 评分仅供训练参考”、实际 Provider/模型和评分维度；
- 将“遗忘曲线”描述改为“基于时间、历史得分和连续成功次数的简化到期度排序”，或正式引入并注明 SM-2/FSRS；
- 保留现有标准答案编辑，后续增加导入前预览、AI 生成标记和修订历史；
- 为删除、批量迁移和助理动作增加操作日志，优先实现软删除或短期撤销；
- 为请求、会话、operation 和 LLM 调用贯通 `request_id`，日志不得记录完整 Prompt、API Key、用户回答或导入文档。

## 12. 暂缓事项

以下事项不进入当前前两阶段：

- 全面迁移到 `modules/*` 业务目录；
- 为每张表建立 Repository；
- 全项目一次性 TypeScript 化；
- 全接口统一 `{data, meta}` 包装；
- 立即启用 `/api/v1`；
- Celery、RQ、Dramatiq 等分布式任务系统；
- 复杂熔断中心和多实例状态同步；
- 一次性创建大量可能很快过时的架构文档。

当项目进入云端、多用户、多 worker 阶段时，应重新评估这些事项。

## 13. 完成定义

本轮修复全部完成需满足：

- 并发或重复提交不会产生重复记录、重复计费或重复推进；
- 所有中断中的会话操作都有明确状态，并可恢复或安全重试；
- Provider 原始异常不会返回前端，故障切换只发生在允许的错误类型上；
- 所有上传入口都有统一、可配置、经过测试的资源上限；
- 数据库导入具备完整性、schema 和数据约束校验，并保持事务回滚和导入前备份；
- 默认后端测试命令在干净环境可执行，无固定个人临时目录；
- CI 自动运行后端测试与覆盖率门禁、前端测试和构建；
- 前端刷新后能恢复服务端会话，演示数据不会冒充真实数据；
- 新增测试覆盖上述成功、失败、重复、并发和恢复路径；
- README 与需求文档同步标明当前本地模式、已实现能力和未来云端能力。
