## 一、Agent 系统架构与核心概念

### 1. 一个完整 Agent 系统有哪些核心模块？与传统 LLM Chatbot 最大区别是什么？

一个完整 Agent 通常包含以下模块：

1. **输入与上下文构建**：接收用户目标，装配系统指令、会话历史、用户偏好、环境状态和可用工具。
2. **意图识别与任务建模**：判断用户到底要查询、生成、修改还是执行操作，并把自然语言目标转成约束、验收标准和任务状态。
3. **Planning**：把目标拆成步骤，分析依赖关系、风险和完成条件；简单任务可以隐式规划，复杂任务通常维护显式计划或状态图。
4. **Memory**：短期记忆保存当前任务状态，长期记忆保存跨会话偏好、事实和经验；记忆不是简单堆历史消息，而是有选择地写入、检索、校验和过期。
5. **Tool Use**：发现并选择搜索、数据库、代码执行、文件、浏览器、业务 API 等工具，生成结构化参数并解析返回值。
6. **Execution / Runtime**：执行“思考—行动—观察—更新状态”的循环，负责重试、超时、并发、权限、审批、取消和恢复。
7. **Reflection / Verification**：检查工具结果和最终产物是否满足目标，可通过测试、规则、第二模型、静态分析或人工审批验证。
8. **Guardrails 与可观测性**：做权限控制、敏感操作拦截、预算限制、审计日志、链路追踪和效果评测。

传统 Chatbot 的核心是“一次输入、一次生成”；Agent 的核心是**围绕目标维护状态，并通过工具改变外部环境，经过多步执行直到达到完成条件**。因此 Agent 的难点不只是模型能力，还包括状态机、工具协议、执行可靠性、权限和可恢复性。

### 2. 设计一个本地 Coding Agent 的整体架构

可以分成六层：

```text
用户 / IDE / CLI
      ↓
交互层：需求澄清、进度更新、审批、结果展示
      ↓
Agent Runtime：任务状态机、Planning、上下文装配、模型路由
      ↓
Coding 能力层：代码检索、编辑补丁、终端、测试、Git、浏览器
      ↓
安全执行层：工作区沙箱、命令策略、权限审批、资源与超时限制
      ↓
存储与观测层：会话、计划、索引、记忆、操作日志、trace、评测数据
```

关键设计如下：

- **Workspace Manager**：识别仓库根目录、Git 状态和用户已有修改；必要时创建隔离 worktree，绝不能误覆盖用户改动。
- **Repository Intelligence**：建立文件树、符号、引用、依赖和可选向量索引。查代码时先用精确搜索和语言服务器，语义检索作为补充。
- **Planner / State Machine**：把任务状态建模为 `understand → plan → edit → test → review → done/blocked`，每步有明确进入条件和退出条件。
- **Context Builder**：只装入相关代码片段、项目规范、当前 diff、错误日志和任务摘要，避免把整个仓库塞进上下文。
- **Model Gateway**：统一多模型接口；可让便宜模型做分类/摘要，强模型做设计和复杂修改。
- **Tool Layer**：至少包含读取/搜索文件、补丁编辑、运行命令、测试、Git diff、静态检查；工具要返回结构化结果。
- **Sandbox & Approval**：读操作默认允许；联网、安装依赖、修改工作区外文件、部署和删除等操作按风险审批。
- **Verifier**：运行目标测试、lint、类型检查，审查 diff 是否超出范围，再根据验收标准判断完成。
- **Recovery**：把计划、已完成步骤、修改文件、测试结果持久化；进程退出后可恢复，而不是重新猜一遍。

一次典型流程是：先读取项目说明和 Git 状态，定位相关代码，形成可验证计划；然后用最小补丁修改，运行针对性测试，失败则基于错误迭代；最后检查 diff、列出验证证据和残余风险。

### 3. Agent 常见设计模式及适用场景

- **ReAct（Reason + Act）**：模型交替进行推理、调用工具、观察结果，再决定下一步。适合路径不确定、需要边查边做的任务，如排查线上故障。优点是灵活，缺点是容易循环、成本不可控。
- **Plan and Execute**：先生成整体计划，再由执行器逐步执行，必要时重规划。适合步骤较多、依赖清晰的长任务，如跨模块重构。缺点是初始信息不足时计划容易过时。
- **Reflection / Self-Refine**：先生成，再批判或验证，再修正。适合代码、报告、SQL 等有明确质量标准的产物，但要防止模型“自我认同”，最好引入测试或独立评审器。
- **Router**：先识别任务类型，再路由到不同模型、工具或子 Agent。适合多业务入口和成本敏感系统。
- **Tool-using Agent / Function Calling Loop**：模型每轮选择一个或多个结构化工具，运行时执行后把结果回传。适合工具边界清晰的业务流程。
- **Graph / State Machine**：把节点、边、条件分支、重试和人工审批显式建模。适合合规、稳定性要求高的生产流程，例如退款、风控。
- **Supervisor–Worker**：主管 Agent 拆分、分派、汇总，Worker 专注独立子任务。适合可并行的研究、测试和多模块分析。
- **Blackboard / Shared Workspace**：多个 Agent 通过共享任务板或结构化状态协作。适合子任务互相提供中间结果的复杂问题。

实际系统通常是混合的，例如“状态图控制主流程 + 节点内部使用 ReAct + 关键产物用 Reflection 验证”。

### 4. 什么是 Agent Harness？

Agent Harness 可以理解为**把模型包裹成可工作的 Agent 的运行时和工程脚手架**。模型负责理解和决策，Harness 负责把决策可靠地落到真实环境中。

它通常提供：Prompt 与上下文装配、工具协议、执行循环、状态持久化、文件和终端接入、沙箱与审批、重试/超时/取消、token 和费用预算、日志追踪、任务恢复以及最终结果渲染。

同一个模型放进不同 Harness，实际效果可能差很多。例如 Coding Agent 能否安全编辑文件、增量读取仓库、在测试失败后继续、保留用户改动，主要取决于 Harness。可以把模型看成“大脑”，Harness 看成“感知系统、手脚、工作台和安全制度”。

### 5. Multi-Agent 如何拆解和协作？

常见流程是：

1. **任务分析**：识别可独立并行的子任务、共享依赖和关键路径。
2. **角色分工**：按能力或数据权限分给不同 Agent，例如研究、后端、前端、测试、审查。
3. **定义契约**：每个子任务明确输入、输出格式、截止条件、允许修改的范围和验收标准。
4. **执行与通信**：通过消息、共享状态或制品传递结果；尽量传结构化结论，不把全部对话互相广播。
5. **冲突解决与汇总**：Supervisor 检查重复、矛盾和覆盖缺口，必要时重新分派。
6. **全局验证**：集成测试或统一评审，验证局部正确能否组成整体正确。

例如开发电商退款功能：一个 Agent 研究现有订单状态机，一个实现退款 API，一个修改前端，一个补测试；但数据库 schema 和接口契约必须先由主管统一。适合并行的是“低耦合、输出可验收”的任务；强顺序依赖或多人同时改同一文件时，多 Agent 反而增加协调成本。

### 6. 用户输入不足以完成规划时如何处理？

不要立即编造，也不要把所有问题一次性抛给用户。比较好的策略是：

- 先利用当前上下文、项目文件、历史约定和只读工具补齐可发现的信息。
- 区分**阻塞信息**和**可用默认值的信息**。只询问会显著改变方案、造成风险或无法逆转的关键问题。
- 提问要具体，并说明影响，例如：“登录态是 Cookie 还是 JWT？这会决定中间件和测试方案。”
- 对低风险细节可以声明假设后继续，如“暂按 PostgreSQL 设计，接口保持数据库无关”。
- 支持渐进式规划：先给高层计划，执行到相关节点再补细节，而不是一开始追求伪精确。
- 如果用户暂时无法回答，给出选项、推荐默认方案和可回滚路径。

核心原则是**最小必要澄清 + 显式假设 + 可逆执行**。

### 7. Agent 从开发到上线要考虑哪些工程因素？

- **需求与边界**：明确任务成功条件、不能做什么、何时需要人工审批。
- **模型与 Prompt 版本管理**：记录模型、参数、Prompt、工具版本，保证问题可复现。
- **工具可靠性**：schema 校验、幂等键、超时、重试、熔断、限流、回滚和错误归一化。
- **状态管理**：任务状态持久化、断点续跑、并发控制、重复消息去重。
- **安全**：最小权限、沙箱、密钥隔离、Prompt Injection 防护、敏感数据脱敏、审计日志。
- **质量与评测**：离线数据集、轨迹评测、工具调用正确率、任务完成率、回归测试和线上 A/B。
- **可观测性**：记录每轮模型输入摘要、工具调用、延迟、token、费用、错误和最终状态，同时控制隐私。
- **性能与成本**：缓存、上下文裁剪、模型分层、并发、流式输出、批处理和预算上限。
- **部署运维**：灰度、回滚、配置中心、容量评估、告警、灾备和供应商降级。
- **人机协同**：高风险动作审批、可取消、可解释的进度、失败后的接管入口。

生产 Agent 不能只看“Demo 能跑”，而要看它在超时、工具失败、模型漂移、重复请求和恶意输入下是否仍然可控。

## 二、工具调用与 MCP

### 8. Agent 调用外部工具有哪些形式？底层原理是什么？

主要形式包括：

- **原生 Function/Tool Calling**：将工具名称、描述和 JSON Schema 随请求发给模型，模型输出结构化调用意图。
- **Prompt 约定 + 解析器**：要求模型输出特定 JSON/XML/DSL，再由程序解析。兼容性强，但不如原生约束稳定。
- **MCP**：客户端通过标准协议连接 MCP Server，动态发现并调用 tools，也可读取 resources 和 prompts。
- **代码/命令执行**：模型生成代码或命令，由沙箱执行器运行。
- **GUI / Computer Use**：模型基于截图或可访问性树生成点击、输入等动作。
- **Agent-to-Agent / Workflow API**：把另一个 Agent 或工作流封装成工具。

底层本质都是一个闭环：**向模型暴露“可做什么” → 模型生成工具选择和参数 → 宿主程序校验并执行 → 把观察结果返回模型 → 模型继续决策或生成答案**。模型通常不直接执行 API，它只产生调用意图；真正的权限、网络和副作用由运行时负责。

### 9. 工具注册、发现与调用的完整流程

1. **注册**：定义工具的唯一名称、用途描述、参数 JSON Schema、返回结构、权限级别、超时和幂等属性，并绑定实际处理函数。
2. **发现**：启动时静态加载，或从插件/MCP Server 动态拉取工具清单；大型系统可先检索工具目录，只向模型暴露候选集。
3. **上下文注入**：将候选工具的名称、描述和 schema 放入模型请求。
4. **模型决策**：模型根据用户目标和上下文，生成 `tool_name + arguments`，有些模型支持并行调用多个工具。
5. **参数校验**：宿主按 schema 校验类型、枚举和必填字段，还要做业务权限检查，不能只信模型输出。
6. **风险控制**：对删除、支付、部署等动作要求确认；为写操作加幂等键和审计信息。
7. **执行**：调用本地函数、RPC、HTTP API 或 MCP；处理超时、重试、限流和取消。
8. **结果归一化**：返回结构化数据、错误码、是否可重试和必要摘要；大结果应分页、截断或存为资源引用。
9. **观察回传**：将结果作为 tool message 关联原调用 ID 返回模型。
10. **继续循环**：模型决定再次调用、修改参数、降级处理或输出最终答案。

### 10. 什么是 MCP？执行流程是什么？

MCP（Model Context Protocol）是连接 AI 应用与外部能力的开放协议。它把“某个客户端如何接某个工具服务”标准化，降低每个 Agent 都手写适配器的成本。

MCP 中通常有三类角色：

- **Host**：承载模型和用户体验的应用。
- **Client**：Host 内与某个 MCP Server 维持协议连接的组件。
- **Server**：对外暴露工具、资源和 Prompt 模板的服务。

典型流程：Host 启动 Client，通过 stdio 或网络传输连接 Server；双方初始化并协商协议版本和能力；Client 请求工具/资源清单；Host 按权限把相关能力提供给模型；模型选择工具后，Host 发起 MCP 调用；Server 执行业务逻辑并返回文本、结构化内容或资源；Host 把结果加入上下文，模型继续生成。过程中还要处理认证、权限、进度通知、取消和错误。

需要强调：MCP 不是模型，也不是 Agent 框架；它是能力接入层的协议。

### 11. MCP 与 Tool Calling 的核心区别

**Tool Calling 是模型与宿主之间的“决策输出机制”，MCP 是宿主与外部能力提供方之间的“连接协议”。**

Tool Calling 规定模型如何表达“我要调用 `search`，参数是这些”；MCP 规定客户端如何发现 `search`、向远端服务发送调用、接收结果。前者更靠近模型 API，后者更靠近系统集成。

两者不是竞争关系，常见组合是：模型通过 Tool Calling 选中工具，Agent Runtime 再通过 MCP 调用对应 Server。即使不用 MCP，也可以用普通 HTTP 或本地函数完成 Tool Calling；即使有 MCP，Host 仍需决定如何把工具描述给模型。

### 12. Skill 与 Tool Calling、MCP 有何不同？

Skill 更像**可复用的任务方法、操作手册和领域工作流**，通常包含何时触发、步骤、约束、模板、示例以及可调用的脚本或工具。它解决的是“Agent 应该怎样把一类任务做好”。

- Tool Calling：解决模型如何表达一次结构化动作。
- MCP：解决外部能力如何以统一协议被发现和调用。
- Skill：解决一类任务的经验、流程和质量标准如何被复用。

例如“生成合规周报”这个 Skill 可能规定先读数据、按模板计算指标、生成图表、复核敏感字段；过程中它可以调用多个 Tool，其中某些 Tool 又由 MCP Server 提供。因此 Skill 是更高层的行为编排与知识封装，不一定产生外部副作用，也不等同于一个 API。

### 13. 如何提升工具调用正确率？

- **工具边界清晰**：一个工具做一件事，名字可区分，避免多个工具描述高度重叠。
- **高质量 schema**：使用明确类型、枚举、格式、必填项、边界值，减少自由文本参数。
- **描述包含触发与禁用条件**：不仅说“能做什么”，还说明“什么时候用、什么时候不要用”。
- **提供少量正反例**：展示正确选工具、参数格式以及常见混淆。
- **两阶段选择**：先检索/路由候选工具，再让模型从小集合中选择。
- **参数校验与自动修复**：schema 验证失败时，把具体错误反馈给模型；确定性字段尽量由程序补充。
- **执行前验证**：高风险调用先让模型或规则确认目标、权限和影响范围。
- **结果可理解**：工具返回稳定结构和明确错误，而不是一大段不可解析日志。
- **轨迹评测**：分别测工具选择准确率、参数准确率、调用顺序、任务成功率，而不是只看最终文本。
- **用业务规则兜底**：权限、金额、路径等关键约束必须由代码保证，不能依赖 Prompt。

### 14. 大量工具导致 Prompt 膨胀，如何优化？

1. **分层工具目录**：先暴露领域级路由工具，如“数据库类、运维类”，选中后再加载具体工具。
2. **语义检索工具**：为工具描述建立索引，根据当前请求召回 Top-K。
3. **命名空间/动态注册**：只加载当前页面、租户、角色或任务阶段可用的工具。
4. **压缩 schema**：删除重复废话和模型不需要的返回字段；公共参数由网关注入。
5. **工具组合**：将频繁连续出现、强耦合的低层调用封装成一个高层业务工具，但不要做成无法控制的“万能工具”。
6. **缓存前缀**：稳定的系统指令和工具定义利用 Prompt Cache，减少成本和首 token 延迟。
7. **模型路由**：小模型先做工具候选分类，强模型只处理最终选择和复杂参数。
8. **按需获取详情**：初始只给名称和一句摘要，模型选中候选后再请求完整 schema。

目标不是把描述压到最短，而是在**可区分性、参数约束和 token 成本**之间平衡。

### 15. 模型如何判断是否调用工具，并生成参数？

在训练阶段，模型学习了自然语言请求、工具定义和正确调用轨迹之间的映射。推理时，工具 schema 会作为特殊上下文提供给模型，模型比较：当前问题能否直接回答、是否需要实时/私有/精确数据、是否需要产生外部动作，以及哪个工具描述最匹配。

当选择工具后，模型按参数 schema 自回归生成结构化 arguments。支持 constrained decoding 的平台会在解码阶段限制输出满足 JSON Schema；否则由宿主解析和校验。

但模型的“判断”不是确定性业务引擎，可能选错、漏调或编造参数。因此系统应配合：`tool_choice` 策略、候选工具过滤、schema 约束、权限规则、缺参澄清、结果校验和失败重试。尤其不能让模型猜订单号、文件路径、用户身份等关键参数。

### 16. 多类模型后端如何统一请求、响应和错误？

建议增加 Model Gateway / Provider Adapter 层，对上暴露统一领域接口，对下适配 OpenAI、Anthropic、本地模型等提供商。

统一请求模型可包含：messages/content parts、system instruction、tools、tool choice、temperature、max tokens、stream、response schema、timeout 和 trace metadata。统一响应可包含：文本片段、工具调用、usage、finish reason、provider/model、原始响应引用。

工程上要注意：

- 用**能力矩阵**描述每个模型是否支持图片、结构化输出、并行工具、长上下文等，不能假设功能完全等价。
- 定义统一错误 taxonomy，如认证、限流、超时、上下文超限、内容安全、模型不可用、可重试服务错误；同时保留 provider 原始错误。
- 只对幂等请求安全重试，采用指数退避和抖动；跨模型 fallback 要记录，因为结果语义可能变化。
- 流式事件统一为 `text_delta/tool_call_delta/usage/completed/error` 等内部事件。
- 做 token 估算、费用统计、trace ID、超时和取消传播。
- Adapter 只处理协议差异，业务 Prompt 和降级策略放在更高层，避免网关变成巨型条件分支。

## 三、RAG 与知识库构建

### 17. RAG 从文档接入到生成答案的完整流程

RAG 分为离线知识库构建和在线检索生成两阶段。

**离线阶段：**

1. 数据源接入：文件、网页、数据库、Wiki、对象存储等。
2. 解析与清洗：提取正文、标题、表格、图片/OCR，去页眉页脚、乱码和重复内容。
3. 文档结构识别：保留章节层级、页码、表格关系和来源权限。
4. Chunking：按语义或结构切分，必要时加入 overlap 和父子关系。
5. 元数据与权限：记录来源、作者、时间、版本、ACL、文档 ID、chunk ID。
6. 向量化和建索引：生成 embedding，写入向量库；同时可建立 BM25/倒排索引。
7. 质量检查：抽样解析、重复率、空 chunk、检索基准和增量更新一致性。

**在线阶段：**

1. 理解问题：识别意图、时间范围、实体、权限和是否需要检索。
2. Query Rewrite/Expansion：结合对话把省略问题改成独立查询，必要时拆成多个子查询。
3. 召回：向量、关键词、元数据过滤或 Hybrid Search。
4. 融合与 Rerank：合并多路结果，使用 RRF 或打分融合，再用 reranker 精排。
5. 上下文构建：去重、选择 Top-N、保留引用、按 token 预算排布。
6. 生成：要求答案基于证据，无法支持时明确说不知道。
7. 后处理：引用校验、格式化、安全过滤、缓存和反馈采集。

### 18. 知识库构建的关键环节

最关键的不是“选哪个向量库”，而是数据质量和评测闭环：

- 数据源是否权威、完整、可追溯，权限是否正确。
- 解析是否保留文档结构，扫描 PDF、表格和图片是否被正确处理。
- 清洗去重是否误删有效信息。
- Chunk 是否保持语义完整，并能回到父文档和精确位置。
- Embedding 是否匹配语言、领域和查询/文档长度。
- 索引是否支持增量更新、删除、版本切换和 ACL 过滤。
- 是否建立真实问题—相关证据的黄金数据集，分别评测解析、召回、排序和生成。

知识库还要有生命周期治理：内容变更检测、重建索引、过期策略、删除传播、血缘和监控。否则检索准确率即使初期很好，也会随时间下降。

### 19. 常见 Chunking 策略

- **固定长度**：按字符或 token 切分，并设置 overlap。简单稳定，但可能切断语义。
- **递归字符切分**：按段落、换行、句子、字符逐级尝试，兼顾长度和自然边界。
- **结构化切分**：按 Markdown 标题、HTML DOM、PDF 章节、代码函数/类切分，通常比固定长度更好。
- **句子/语义切分**：计算相邻句向量差异，在语义转折处切分；质量较好但成本更高、结果不够稳定。
- **滑动窗口**：每个块重叠较多，适合答案跨边界，但索引和去重成本高。
- **Parent–Child**：小块用于精确召回，命中后返回更大的父块供生成。
- **多粒度索引**：标题、摘要、段落、章节同时索引，适合长文和多层问题。
- **特定类型切分**：代码按 AST，表格按行组并携带表头，对话按轮次和主题。

Chunk 大小没有通用最优值，要根据答案跨度、模型窗口、embedding 上限和真实评测选择。

### 20. RecursiveCharacterTextSplitter 的逻辑及中文注意点

它接收一组从粗到细的分隔符，例如 `\n\n → \n → 空格 → 字符`。算法先用最粗分隔符切分；如果片段仍超过 `chunk_size`，就在该片段上递归使用更细的分隔符；最后将小片段重新合并到目标大小，并保留指定 overlap。它不是严格的语义算法，而是尽量在自然边界内满足长度限制。

中文要注意：

- 中文没有天然空格，默认空格分隔作用很小，应加入 `。！？；、`、中文换行和全角标点。
- `chunk_size` 的计量要明确是字符还是 token。不同 tokenizer 下中文字符与 token 不是一比一。
- 避免把标题和正文、列表序号和内容、表头和表体拆开。
- 清洗 PDF 换行时不能把每行误当段落；同时保留真正的章节边界。
- overlap 应覆盖可能跨句的上下文，但过大会造成重复召回。
- 对法规、合同、代码和表格，优先用结构化 splitter，递归字符切分只作为兜底。

### 21. 如何解析表格与图片？

**表格：**优先使用原生结构解析，例如 DOCX 表格、Excel 单元格、HTML table；PDF 可用坐标、线框和版面模型恢复行列。输出不要只保留一串文本，要保存表名、表头、行列关系、合并单元格、页码和来源。用于检索时可按“表格摘要 + 行组”索引，每个行组重复携带表头；复杂计算最好让 SQL/DataFrame 工具处理，而不是让 LLM 只读序列化文本。

**图片：**先分类。扫描文档用 OCR；流程图、截图、图表可用视觉模型生成描述并抽取关键实体；图表还可做坐标轴、图例和数据点识别。保存原图引用、OCR 文本、视觉描述、位置和置信度，并与附近标题/段落关联。

必须做抽样可视化检查，因为表格错列、OCR 数字错误往往会产生“看起来合理但完全错误”的答案。财务、医疗等场景要设置低置信度拒答或人工复核。

### 22. 如何提升知识检索的回答正确率？

可以按“数据—召回—排序—生成—评测”五层优化：

- 数据层：提升解析质量，去重，补元数据，保证更新和权限正确。
- 召回层：领域适配 embedding、Query Rewrite、多查询、Hybrid Search、元数据过滤和合适 Top-K。
- 排序层：RRF 融合、cross-encoder/LLM rerank、MMR 去冗余。
- 上下文层：父子块扩展、相邻块补全、引用保留、控制噪声和顺序。
- 生成层：要求逐条基于证据，证据不足拒答；生成后做引用一致性或事实核验。
- 评测层：分别衡量 Recall@K、MRR/nDCG、上下文精确率、faithfulness、答案正确率，而不是只看主观感觉。

很多“生成幻觉”其实是上游没召回证据；也有些“召回不错但回答错”是上下文噪声或生成没有受证据约束，需要分层诊断。

### 23. 召回差时如何定位？各环节优先级如何？

不要一上来就换 Embedding 或加 Rerank。推荐顺序是：

1. **先建可复现样本**：为失败问题标出目标文档和目标 chunk，确认知识库里确实存在答案。
2. **检查接入和解析**：目标内容是否被漏解析、乱码、错表、被权限过滤或索引版本过旧。
3. **检查 Chunk**：答案是否被切碎，标题/表头是否丢失，块过大导致主题稀释，块过小导致信息不完整。
4. **基线召回**：分别跑 BM25 和向量检索，观察目标 chunk 的 rank 和分数。
5. **检查 Query**：多轮省略、别名、缩写、口语词是否与文档表达不一致；此时再做 Rewrite/Expansion。
6. **Hybrid Search**：当关键词和语义各有优势时融合，专有名词、编号和错误码尤其依赖关键词。
7. **Rerank**：它只能重排已召回候选，目标根本没进候选集时无效。因此应在召回覆盖率足够后使用。
8. **最后评估 Embedding**：用相同数据和指标做模型 A/B，而不是凭榜单替换。

所以一般优先级是：**数据/权限/索引 → 解析 → Chunk → Query 与召回策略 → Hybrid → Rerank → Embedding A/B**。具体项目仍要由失败样本决定。

### 24. Embedding 模型如何选择？会产生什么影响？

选择维度包括：

- 语言与领域：是否擅长中文、代码、法律、医疗等。
- 检索任务：对称相似度还是 query-document 非对称检索，是否支持 instruction/prefix。
- 最大输入长度与截断策略。
- 向量维度、存储、查询延迟和价格。
- 是否支持本地部署、隐私要求和批量吞吐。
- 与现有数据的真实 Recall@K、MRR/nDCG 表现。

不同模型会改变语义空间：同义表达、长文本主题、专有名词、跨语言和代码结构的相似度都会不同。维度更高不必然更准，但会增加存储和检索成本；模型升级通常需要整库重新向量化，且新旧向量不能随意混用。

正确做法是用真实 query—relevant chunk 数据集评测，并固定 Chunk、索引和搜索参数做 A/B；同时观察延迟与费用。关键词强的场景即使换更强 Embedding，也往往仍需要 Hybrid Search。

### 25. RAG、Memory、Context Engineering 分别解决什么？在 Coding Agent 中如何组合？

- **RAG**解决“当前问题需要哪些外部知识”。它从代码库、文档、Issue、API 文档中按需检索证据。
- **Memory**解决“跨步骤或跨会话应该记住什么”。例如用户偏好、架构决策、任务进度和已经验证的事实。
- **Context Engineering**解决“这一轮模型究竟应该看到什么，以及如何组织”。它统筹系统指令、当前目标、代码片段、检索结果、记忆、工具和 token 预算。

Coding Agent 中可以这样组合：短期 Memory 保存当前计划、已修改文件和测试状态；长期 Memory 保存稳定的项目约定，但必须带来源和版本；RAG 根据当前子任务检索相关符号、调用链、项目文档和历史 Issue；Context Builder 对这些材料去重、排序、裁剪，把关键约束放在明显位置。

例如修复支付回调 Bug：RAG 找到 handler、签名校验和测试；Memory 记住用户要求不能改变公开 API、之前尝试失败的原因；Context Engineering 只把当前 diff、相关函数、错误日志和验收标准装入模型，而不是把整段会话与整个仓库全部塞进去。

## 四、Memory 与上下文管理

### 26. Agent 中的 Memory 如何实现？短期与长期记忆解决什么？

Memory 不是单一数据库，而是一套**写入、表示、存储、检索、校验、更新和遗忘**机制。

- **短期记忆 / Working Memory**：服务当前任务，保存最近对话、当前计划、变量、工具结果、失败尝试和待办。常放在上下文窗口、任务状态表或 checkpoint 中，生命周期与任务接近。它解决多步执行的连续性。
- **长期记忆**：跨任务或跨会话保存稳定信息，如用户偏好、项目约定、已确认架构决策和可复用经验。可存在关系库、文档库、向量库或知识图谱中。它解决长期个性化和经验复用。

从内容还可分为：语义记忆（事实）、情景记忆（某次任务发生了什么）和程序性记忆（怎样完成一类任务，类似 Skill）。长期记忆必须记录来源、时间、置信度、作用域和版本，不能把模型随口生成的内容直接当事实写入。

### 27. 如何设计完整的记忆检索流程？

**写入：**

1. 从对话和工具结果中提取候选记忆。
2. 判断是否值得长期保存：是否稳定、未来有用、非敏感、非重复。
3. 区分“用户明确陈述”“工具验证事实”“模型推断”，赋予不同置信度。
4. 归一化为结构化记录：内容、类型、实体、scope、source、timestamp、version、TTL。
5. 去重、合并或建立 supersedes 关系，再持久化。

**召回：**

1. 根据当前请求生成检索查询并确定作用域，例如当前用户 + 当前仓库。
2. 先用实体、时间、权限等过滤，再做关键词/向量召回。
3. 综合相关度、重要性、新鲜度、可信度和使用频率排序。
4. 去冲突、去重复；对可能过时的事实回源验证。
5. 在 token 预算内压缩并注入上下文，同时保留来源。
6. 记录哪些记忆被使用以及是否帮助了任务，作为后续治理信号。

历史消息不应全部存成长期记忆。一般只保存稳定偏好、明确决策、未完成承诺和经验证事实；临时情绪、一次性参数、模型猜测通常不保存。

### 28. 分层记忆各层的写入、召回与失败策略

一个实用的四层设计是：

| 层级 | 写入时机 | 召回条件 | 失败策略 |
|---|---|---|---|
| 当前窗口 | 每轮消息和少量工具结果 | 默认可见 | 超限时裁剪低价值 observation |
| 任务状态/Checkpoint | 步骤完成、决策、修改、错误后 | 恢复任务或进入下一步 | 以持久化状态和实际环境为准重新对账 |
| 会话/项目记忆 | 阶段结束时提取稳定结论 | 同一任务、项目或仓库相关请求 | 过期时回读文件/Git/数据库验证 |
| 用户长期记忆 | 用户明确偏好或多次稳定行为 | 当前用户且语义相关 | 冲突时优先当前明确指令，并标记旧记忆失效 |

写入应有阈值，避免“每句话都记”；召回应有 token 预算和最小相关度；失败时应能在无长期记忆的情况下降级运行。记忆是辅助信息，不应成为唯一事实来源。对影响写操作的关键事实，如目标分支、账号、支付金额，必须实时确认或从权威系统读取。

### 29. 如何解决多轮任务的上下文膨胀？

可以采用“保留原始事实，压缩过程噪声，按需重新取回”的策略：

- 将上下文分成稳定系统指令、当前任务状态、最近对话、按需检索材料。
- 工具长输出落盘或存对象存储，只在上下文保留摘要、定位信息和结果 ID。
- 把旧对话压成结构化任务摘要：目标、约束、已完成、未完成、决定、失败原因、关键引用。
- 代码只保留相关函数和当前 diff；需要时再按符号/行号读取，不重复塞整个文件。
- 用 checkpoint 代替完整轨迹回放，失败恢复时读取状态而不是全部历史思考。
- 给不同内容分配 token 预算，优先保留用户最新指令、不可逆约束、当前错误和验收标准。

例如 Coding Agent 连续改十个文件时，不应每轮携带十次测试的完整日志。可保留“当前失败测试名 + 最后一次错误栈 + 已排除原因”，完整日志以文件引用保存；已经稳定完成的步骤压缩成一行状态。

### 30. 如何判断当前请求是否被“压缩损坏”？

压缩损坏指摘要遗漏、歪曲或合并了会影响当前决策的信息。可以做以下检查：

- **约束完整性**：当前摘要是否包含目标、禁止项、接口契约、验收标准和用户最新修改。
- **可回答性对比**：用原始上下文与压缩上下文分别回答关键状态问题，比较差异。
- **事实一致性**：摘要中的文件、参数、数字、状态能否从原始消息或工具结果回溯。
- **决策敏感性测试**：删除某条摘要后计划是否改变；如果关键决策依赖一条无来源信息，应回源。
- **冲突检测**：用户新指令是否被旧摘要覆盖，多个摘要是否互相矛盾。
- **任务探针**：压缩后让系统回答“目标是什么、做到哪了、哪些约束不能破、下一步是什么、证据在哪里”。答不全就不能继续高风险执行。

高风险动作前最好重新读取原始权威信息，而不是只信压缩摘要。

### 31. 任务摘要、文件摘要如何治理并防止信息丢失？

- 使用结构化模板，不只写自由文本：目标、范围、约束、决策、证据、未完成、风险、更新时间。
- 每条重要结论保留 source pointer，如消息 ID、文件路径 + 内容哈希、commit、工具结果 ID。
- 摘要带生成模型/版本、时间和覆盖范围，支持审计与重建。
- 摘要是派生缓存，不覆盖原始数据；原始会话、文件和工具结果按策略保留。
- 文件变化后按 hash/mtime/commit 使旧摘要失效，采用增量重建。
- 对数字、API、否定约束等高价值字段做抽取式保留，避免纯生成式改写。
- 多层摘要要防止反复“摘要的摘要”造成漂移，可定期从原始材料重新生成。
- 建立摘要质量评测：事实覆盖率、矛盾率、可追溯率和关键约束召回率。

### 32. 过时文件摘要或错误过程笔记如何检查、纠正与弃用？

首先把记忆记录与事实版本绑定：文件摘要记录路径、内容哈希或 commit；过程笔记记录任务 ID、工具证据和生成时间。召回时若当前 hash/commit 不匹配，就标记 stale，不直接注入。

纠正流程可以是：发现冲突 → 回读当前文件/Git/测试结果 → 判断权威来源 → 写入新记录 → 用 `supersedes` 指向旧记录 → 旧记录软删除或降权 → 重建相关索引。不要静默覆盖，否则无法审计错误来自哪里。

对过程笔记还应区分“尝试”“推断”“验证结论”。例如“怀疑缓存有问题”不能被后续当成事实；只有“测试 X 复现并由日志 Y 证实”才能提升置信度。定期做 TTL 清理、未被引用记忆清理和源文件一致性扫描。

### 33. 模型幻觉写入错误记忆，后续如何纠正？

预防比事后修复重要：

- 模型生成内容默认是候选，不是已验证事实。
- 只有用户明确陈述或工具/权威数据验证的内容才能高置信写入。
- 记录 provenance 和置信度；推断要明确标记。
- 敏感或影响决策的记忆写入前要求确认。

发现错误后，应回源核验，将错误记录标记为 `invalid/retracted`，写入正确记录并建立替代关系；从向量索引和缓存中同步撤下错误版本；找到引用该记忆的任务或派生摘要并级联失效。后续召回若存在冲突，优先当前用户指令和权威工具结果，并可向用户说明已纠正。不要通过“再写一条相反记忆”来碰运气，否则两条都可能被召回。

## 五、意图识别

### 34. 意图识别有哪些实现方式？分别适用什么场景？

- **规则匹配**：关键词、正则、前缀命令、状态机。适合意图少、边界稳定、要求低延迟和强可解释的场景，如 `/help`、验证码。缺点是维护成本随表达多样性上升。
- **传统/小模型分类**：TF-IDF + 逻辑回归、BERT 类分类器等。适合标签稳定、有一定标注数据、高吞吐低成本场景。上线后需要处理类别漂移和未知意图。
- **LLM 分类**：Zero-shot/Few-shot 或结构化输出。适合标签经常变化、语义复杂、数据少或需要同时抽取槽位的场景。缺点是成本、延迟和稳定性。
- **Embedding 相似度**：将请求与意图描述/示例比较。适合快速冷启动和长尾扩展，但相近意图边界可能不清晰。
- **混合路由**：高精度规则优先，常见意图用小模型，低置信或复杂样本交给 LLM，最终提供 unknown/人工入口。生产中最常见。

### 35. LLM 意图分类如何选 Zero-shot / Few-shot？数据少时如何稳定？

标签定义清晰、彼此差异大、模型对领域熟悉时先用 Zero-shot，迭代快；意图边界细、业务术语特殊、容易混淆或输出格式不稳定时使用 Few-shot。示例不在多，而在覆盖决策边界、易混淆对和 unknown 情况。

数据少时可以：

- 写清每个标签的正定义、反定义和优先级。
- 从真实流量挑代表性、边界和反例，不只放标准句。
- 要求结构化输出 `intent/confidence/required_slots`，并做 schema 校验。
- 设置 unknown 和低置信兜底，不强迫所有请求归类。
- 用规则预处理明确命令，用 embedding 找近邻示例动态放入 Prompt。
- 多次评测不同措辞、温度设低、固定模型版本。
- 用少量人工标注做校准集，持续分析混淆矩阵；可用 LLM 辅助扩充数据，但必须人工抽检。

### 36. 意图识别模块通常如何落地？

完整模块通常包括：文本标准化与必要的上下文拼接 → 高优先级规则 → 分类器/LLM → 置信度校准 → 槽位抽取 → 策略路由 → unknown/澄清 → 日志反馈。

接口可以统一为：

```json
{
  "intent": "refund_order",
  "confidence": 0.91,
  "slots": {"order_id": "..."},
  "missing_slots": [],
  "alternatives": ["query_refund_status"]
}
```

要特别处理多意图、上下文依赖和 OOD（分布外）请求。评测除总体准确率外，还看各类 Precision/Recall/F1、混淆矩阵、unknown 召回、路由后任务成功率和业务损失。分类准确不代表业务成功，例如“退款”识别正确但订单号抽错，结果仍然失败。

## 六、Prompt 工程与幻觉控制

### 37. Prompt 如何组织？System、Few-shot、CoT 各自作用是什么？

常见优先级是：系统/开发者规则 → 用户目标 → 当前任务状态和证据 → 工具描述 → 输出要求。设计时要明确角色、目标、边界、上下文、流程、异常处理和验收标准，并把外部内容标记为数据而非指令。

- **System Prompt**：定义长期稳定的角色、行为边界、安全规则、工具使用原则和输出契约。不要塞入每次变化的业务数据。
- **Few-shot**：用示例展示任务映射、风格和边界，特别适合分类、信息抽取和固定格式。例子要代表真实难点，避免泄漏错误模式。
- **CoT**：通过中间推理提高复杂问题表现。工程上更重要的是让模型进行必要的内部推理或输出简洁的可验证依据，而不是强制暴露冗长思维过程。对生产系统，应优先要求计划、证据、计算步骤或工具轨迹这些可审计产物。

### 38. Prompt 常见结构

可以用以下模板：

```text
Role：你是谁、服务什么目标
Task：本轮具体任务
Context：必要背景、数据和当前状态
Constraints：必须/禁止、权限、范围、时效
Tools：可用工具及调用原则
Procedure：建议步骤或状态机
Output Contract：格式、字段、长度、引用方式
Examples：少量正反例
Failure Policy：信息不足、冲突、工具失败时怎么办
```

常见变体还有：分类 Prompt（标签定义 + 决策规则 + 示例）、RAG Prompt（问题 + 证据 + 引用/拒答要求）、Agent Prompt（目标 + 工具 + 循环与完成条件）、结构化抽取 Prompt（schema + null 规则）。结构要服务任务，不是每个 Prompt 都要把所有章节写全。

### 39. Prompt 层面的优化手段

- 指令具体、可验证，避免“尽量做好”这类模糊要求。
- 分离指令和数据，用标签或明确分隔符降低 Prompt Injection 风险。
- 重要约束放在开头或临近输出处，必要时在结束前简短重申。
- 给模型明确的成功标准、失败策略和拒答条件。
- 让输出遵循 JSON Schema、固定模板或枚举，减少解析不确定性。
- 用代表性 Few-shot 和反例说明边界。
- 将复杂任务拆成分类、检索、生成、验证等阶段，不强求一个 Prompt 做完全部。
- 删除重复、冲突和无关上下文；Prompt 越长不等于越好。
- 建 Prompt 版本、回归集和 A/B 测试，以任务成功率、格式正确率、成本和延迟评估，而不是凭感觉改词。

### 40. 如何降低幻觉？除 Prompt 外有哪些工程方案？

- 用 RAG、数据库和搜索给出可追溯证据。
- 对实时、数值、身份、权限等信息强制调用权威工具。
- 使用结构化输出和 schema 校验，约束形式但要注意它不能保证事实正确。
- 生成后做引用一致性、规则、计算器、单元测试或第二模型验证。
- 设置信心/证据阈值，证据不足时拒答或转人工。
- 采用较低随机性、合适模型，并用领域评测选择，而非盲目追求大模型。
- 把“事实”“推断”“建议”分开表述，要求列出来源。
- 长上下文先检索和去噪，避免模型在冲突材料中随意选择。
- 不让模型直接决定高风险业务结果，由确定性规则和审批兜底。
- 建线上反馈闭环，对幻觉样本做分层归因：检索漏召回、证据冲突、模型不忠实还是工具数据错误。

### 41. 如何提升模型回答性能？

“性能”要先拆成质量、延迟、吞吐和成本：

- **质量**：更好的任务定义、上下文质量、RAG、工具、分步推理、验证和针对性微调。
- **延迟**：缩短 Prompt、减少串行调用、并行独立检索、流式输出、缓存、选择更快模型、限制无效重试。
- **吞吐**：异步 I/O、批量 embedding、连接池、队列、限流和弹性扩容。
- **成本**：模型分层路由、Prompt Cache、结果缓存、压缩工具输出、控制最大 token、简单任务用小模型。

优化时建立基线和 SLO，用代表性数据看任务成功率、P50/P95 延迟、token、单任务费用。单独降低 token 可能损害质量，单独换大模型可能让延迟和成本失控，需要看整体 Pareto 平衡。

### 42. 如何解决 Lost in the Middle？

Lost in the Middle 指模型对长上下文中间部分的信息利用率较低。常见办法：

- 不把全部材料直接拼接，先检索、Rerank、去重，只保留高相关内容。
- 将最重要的目标、约束放在开头，关键证据和输出要求放在靠近问题的位置。
- 对长文分层摘要：先章节摘要，再检索原文片段；摘要保留引用。
- 将复杂问题拆成子问题，分别检索和回答后再汇总。
- 按主题组织上下文，给每段清晰标题、来源和编号，避免无结构文本墙。
- 对多个候选证据采用 map-reduce、迭代读取或工具按需获取。
- 用评测验证不同上下文位置上的信息召回率，而不只是扩大窗口。

## 七、执行保护机制

### 43. 重复调用、无法结束或循环时如何保护？

要同时使用确定性护栏和语义判断：

- 最大轮数、最大工具调用数、墙钟超时、token/费用预算。
- 每种工具的调用频率、并发和连续失败上限。
- 维护任务状态图，只允许合法状态转移，明确 `done/failed/blocked/cancelled`。
- 检测重复调用指纹和“状态无进展”，触发参数修正、换方案或停止。
- 对错误分类：可重试错误指数退避，不可重试错误立即停止；设置熔断。
- 要求每步产生可观察进展，如新证据、文件变化、测试状态变化。
- 结束判定基于验收条件和 verifier，而不是完全依赖模型说“完成了”。
- 超限时输出已完成、失败原因、当前状态和下一步建议，支持人工接管或恢复。

### 44. 如何判断和拦截重复工具调用？

为每次调用生成规范化指纹，例如：

```text
fingerprint = hash(tool_name + canonical_json(arguments) + relevant_state_version)
```

canonical JSON 要排序 key、规范路径和默认值；`relevant_state_version` 很重要，因为同样读取一个文件，但文件已变化时不应视为无效重复。

系统维护滑动窗口，发现相同指纹连续出现时比较结果摘要和全局状态：如果参数相同、结果相同且没有新状态，就是强重复；参数略有变化但语义等价，可用规则或 embedding 检测弱重复。拦截后向模型返回“此前已调用、结果引用、为什么无进展”，要求选择继续使用缓存、改变参数或停止。

白名单也必要：轮询异步任务、分页、重试暂时性错误属于合法重复，但应有间隔、cursor、退避和总次数上限。

### 45. 任务恢复机制如何设计？

核心是**事件日志 + checkpoint + 幂等执行**：

- 为任务分配稳定 task ID，持久化目标、约束、计划、当前节点、关键上下文和预算。
- 每个工具调用记录 request ID、参数、开始/完成状态、结果引用和副作用。
- 在关键节点原子写 checkpoint；恢复时从最后一致状态开始。
- 写操作使用幂等键或先查询后写，避免恢复后重复扣款、发消息、创建资源。
- 对“已发出但未收到结果”的不确定调用，先向外部系统对账，不能直接重放。
- 保存模型、Prompt、工具版本，便于复现；环境已变化时触发重新规划。
- 恢复前检查代码/Git/文件、凭据和权限是否仍与 checkpoint 一致。
- 支持取消、人工修改计划和从指定安全节点重启。

### 46. 如何优化 Follow-up 阶段重复读取文件？

- 建立本轮文件缓存，以绝对路径 + 内容哈希/mtime + Git blob ID 作为版本键。
- 工具返回内容时同时返回 hash、行范围和摘要；后续若版本未变直接复用。
- 监听文件变化或在写入后主动使缓存失效，而不是按固定时间盲目失效。
- Follow-up 先读取“上次任务摘要 + 文件版本清单 + diff”，只对变化文件增量读取。
- 用符号索引或行范围读取相关部分，避免重新读取整个大文件。
- 把已确认的稳定项目规范单独缓存，但版本变化后重新加载。
- 如果用户问的是解释/总结，可直接使用已有证据；如果要执行写操作，则在修改前校验目标文件版本，防止基于旧内容打补丁。

缓存优化不能牺牲一致性。最稳妥的是乐观并发：生成补丁时带预期 hash，应用前发现不一致就重新读取并重算。

## 八、框架与生态

### 47. LangChain、LangGraph、n8n 分别是什么？LangChain 有什么特点？

了解。三者所处层次不同：

- **LangChain**：面向 LLM/Agent 应用的开源开发框架，提供统一模型接口、工具、消息、Prompt、检索器、结构化输出和 Agent 抽象，并有大量第三方集成。优势是生态丰富、上手快、组件可组合；代价是抽象层较多、版本演进较快，复杂生产逻辑仍需自己治理。
- **LangGraph**：更低层的有状态编排框架/运行时，用图表达节点、条件边和循环，强调持久化、长任务恢复、流式输出和 Human-in-the-loop。适合“确定性流程 + Agent 自主决策”混合的复杂系统。当前 LangChain 的 Agent 运行在 LangGraph 之上。[LangChain 官方概览](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview)
- **n8n**：通用低代码工作流自动化平台，以可视化节点连接 SaaS、数据库、Webhook 和脚本，也能加入 LLM/Agent 节点。它更偏业务集成和流程自动化，而非专门的 Agent 推理框架。

选择上：快速做模型/工具集成可以用 LangChain；需要显式状态、循环、恢复和审批时考虑 LangGraph；大量 SaaS 连接和运营流程自动化更适合 n8n。生产项目也可以组合使用。

### 48. LangChain 的核心组件有哪些？LCEL 比传统 Chain 有何改进？

经典核心组件包括：

- Models：Chat Model、Embedding。
- Prompts / Messages：Prompt 模板和消息表示。
- Output Parsers / Structured Output：解析和约束模型输出。
- Documents / Loaders / Splitters：文档接入和切分。
- Retrievers / Vector Stores：检索抽象和向量存储。
- Tools / Toolkits：外部能力封装。
- Agents / Middleware / Memory：工具循环、行为扩展和状态。
- Callbacks / Tracing：运行观测；生态中通常配合 LangSmith。

LCEL（LangChain Expression Language）用 `Runnable` 统一组件协议，并用类似 `prompt | model | parser` 的声明式方式组合。相较早期为每种流程编写特定 Chain 类，它带来的主要改进是：

- 组合方式统一，组件更易替换、复用和测试。
- 原生支持 invoke、batch、stream、async 等执行方式。
- 支持并行、分支、fallback、retry 和配置传递。
- 运行结构更容易追踪和可视化。

不过 LCEL 更适合数据流式组合；涉及长期状态、复杂循环、人工中断和恢复时，通常用 LangGraph 表达更清楚。

### 49. 对 AI Agent 有哪些了解？是否实践过 RAG、Skill？

这是一道经历题，不能只背概念。推荐按“认知—项目—难点—结果—反思”回答，并替换成自己的真实经历：

> 我理解 Agent 的核心不是简单套一层 Prompt，而是模型在 Harness 中围绕目标维护状态，通过工具与环境交互，并由规划、记忆、执行保护和验证组成闭环。我做过一个【填写真实项目】。RAG 部分负责接入【数据源】，经过解析、分块、Embedding、Hybrid Search 和 Rerank，把证据提供给模型；Skill 则把【某类重复任务】的步骤、模板、异常处理和工具使用方式封装起来。项目里最难的不是调用模型，而是【真实难点，例如 PDF 表格解析、召回评测、工具幂等或上下文膨胀】。我用【真实方案】解决，最终【填写可量化结果，如 Recall@10、任务成功率、P95、人工耗时变化】。如果重做，我会更早建立分层评测和失败样本集。

如果没有真实生产经验，就坦诚说做过原型或学习项目，重点讲清数据、指标、失败案例和改进，不要虚构线上规模。

## 九、模型基础

### 50. Token 与字符有什么区别？

字符是文本书写单位，例如汉字、字母、标点；Token 是模型 tokenizer 将文本编码后的离散单元，是模型计算上下文长度和费用的基本单位。

Token 可能是一个字符、一个词、词的一部分，甚至与空格组合。英文常见词可能是一个 token，生僻词会拆成多个；中文一个汉字可能对应一个或多个 token，具体取决于 tokenizer。因此不能用固定的“1 token = N 个字符”做精确计算。

模型流程大致是：文本 → tokenizer → token ID → embedding → Transformer。上下文上限通常按输入 token + 输出 token 计算。工程上应使用目标模型的 tokenizer 或官方 usage 统计，尤其要考虑代码、JSON、中文和特殊字符的差异。

### 51. Function Calling 与 Tool Calling 的执行流程分别是什么？

Function Calling 最初通常指“向模型提供函数 schema，模型返回函数名和参数”；Tool Calling 是更通用的概念，工具不一定只是函数，也可能是搜索、代码执行、文件检索、浏览器等，并可能支持一次返回多个调用。很多平台现在把 Function Calling 视为 Tool Calling 的一个子集，实际 API 名称因供应商而异。

**Function Calling 流程：**应用定义函数及 JSON Schema → 随请求发给模型 → 模型返回 function call → 应用校验参数并执行本地/远端函数 → 将函数结果带调用关联信息回传 → 模型生成最终回答。

**Tool Calling 流程：**注册或发现多类工具 → 按任务筛选候选工具 → 模型生成一个或多个 tool calls → Runtime 做 schema、权限和风险校验 → 执行工具 → 以 tool result/observation 回传 → 模型继续调用或结束。

两者都要强调：模型输出的是调用意图，不会自动执行函数；真正执行和承担副作用的是宿主程序。

## 十、工程基础

### 52. 线程池的核心参数及工作原理

以 Java `ThreadPoolExecutor` 为例，核心参数有：

- `corePoolSize`：核心线程数。
- `maximumPoolSize`：最大线程数。
- `keepAliveTime` + `unit`：非核心空闲线程的存活时间；开启核心线程超时后也可作用于核心线程。
- `workQueue`：等待队列，如有界 `ArrayBlockingQueue`、无界 `LinkedBlockingQueue`、直接移交的 `SynchronousQueue`。
- `threadFactory`：线程命名、优先级、是否 daemon、未捕获异常策略。
- `RejectedExecutionHandler`：线程和队列都满后的拒绝策略，如 Abort、CallerRuns、Discard、DiscardOldest。

提交任务后的典型顺序：

1. 运行线程少于 core：创建核心线程执行任务。
2. 否则尝试入队。
3. 队列满且线程少于 max：创建临时线程执行。
4. 队列满且线程达到 max：执行拒绝策略。

这里一个常见误区是“先扩到最大线程再排队”；Java 默认策略实际是先 core、再队列、队列满后才扩到 max。无界队列几乎不会触发扩容到 max，也可能造成任务堆积和内存风险。

### 53. 为什么同时设计核心线程数和最大线程数？何时使用临时线程？

核心线程数提供稳定处理能力，避免频繁创建销毁线程；最大线程数提供突发流量下的弹性，并给资源使用设置硬上限。

当核心线程都忙且等待队列已满时，线程池才会创建 core 之外的临时线程，直到 maximum。临时线程空闲超过 keepAliveTime 后回收。使用有界小队列或 `SynchronousQueue` 时更容易触发临时线程；使用无界队列通常不会。

参数要按任务类型和下游容量设置：

- CPU 密集：线程数通常接近 CPU 核数或核数 + 1，避免过多上下文切换。
- I/O 密集：可以更多，近似参考 `Ncpu × (1 + 等待时间/计算时间)`，但还要受数据库连接池、外部 API 限流约束。
- 最大线程不能只追求吞吐，否则会把压力传给数据库或导致内存、调度开销爆炸。队列、线程数、拒绝策略和监控要一起设计。

### 54. 进程、线程、协程的区别

| 维度 | 进程 | 线程 | 协程 |
|---|---|---|---|
| 资源隔离 | 独立地址空间，隔离强 | 共享进程内存 | 运行在线程内，共享线程/进程资源 |
| 调度者 | 操作系统 | 操作系统 | 用户态运行时/事件循环 |
| 切换成本 | 较高 | 中等 | 较低 |
| 通信 | IPC、管道、共享内存等 | 共享变量，需同步 | 通常通过 await/channel，仍要防共享状态问题 |
| 故障影响 | 单进程崩溃隔离较好 | 可能拖垮整个进程 | 异常处理不当也影响所属线程/事件循环 |
| 适用 | 强隔离、多核并行、独立服务 | 并行计算、阻塞 I/O | 大量并发 I/O、异步任务 |

协程是协作式调度，遇到 `await` 主动让出执行权；它并不天然等于多核并行。CPU 密集任务若只跑在单线程事件循环上仍然会阻塞，需要多进程、线程或专用计算池。

### 55. HashMap 的原理

以 Java 8+ 为例，`HashMap` 底层是**数组 + 链表 + 红黑树**。Key 经 `hashCode()` 和高位扰动得到 hash，通过 `(n - 1) & hash` 定位桶，因此容量通常保持 2 的幂。

`put` 流程：计算桶位置；桶为空直接插入；否则比较 hash 和 `equals`，同 key 覆盖 value，不同 key 加入链表；冲突链较长且数组容量达到阈值时可能树化。Java 8 中常见树化阈值为 8，最小树化容量为 64；元素减少时可能退化回链表。

当 `size > capacity × loadFactor` 时扩容，默认负载因子 0.75。容量翻倍后，旧节点依据 hash 的新增高位拆到“原索引”或“原索引 + 旧容量”，不必完全重新计算位置。

平均查找/插入是 O(1)，严重冲突的链表是 O(n)，树化后是 O(log n)。`HashMap` 允许一个 null key 和多个 null value，不保证顺序，也不是线程安全的。Key 应正确实现 `hashCode/equals`，且放入后不要修改参与哈希的字段；并发场景通常用 `ConcurrentHashMap`。

## 十一、算法编程

### 56. 除自身以外数组的乘积（LeetCode 238）

思路是把答案拆成“当前位置左侧所有元素的乘积 × 右侧所有元素的乘积”，不使用除法。

第一遍从左向右，让 `ans[i]` 保存 `i` 左侧乘积；第二遍从右向左，用变量 `right` 累积右侧乘积并乘到 `ans[i]`。

```java
class Solution {
    public int[] productExceptSelf(int[] nums) {
        int n = nums.length;
        int[] ans = new int[n];

        // ans[i] 先保存 nums[i] 左侧所有数的乘积
        ans[0] = 1;
        for (int i = 1; i < n; i++) {
            ans[i] = ans[i - 1] * nums[i - 1];
        }

        // right 保存当前位置右侧所有数的乘积
        int right = 1;
        for (int i = n - 1; i >= 0; i--) {
            ans[i] *= right;
            right *= nums[i];
        }

        return ans;
    }
}
```

- 时间复杂度：O(n)。
- 空间复杂度：O(1) 额外空间；返回数组不计入额外空间。
- 不需要特殊处理 0：前后缀方法天然支持一个或多个 0。

### 57. 合并重叠区间（LeetCode 56）

先按区间起点升序排序。遍历时，若当前区间起点 `<=` 已合并区间的终点，说明有重叠，更新终点为两者最大值；否则把当前区间作为新结果。

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

class Solution {
    public int[][] merge(int[][] intervals) {
        if (intervals == null || intervals.length == 0) {
            return new int[0][];
        }

        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));
        List<int[]> merged = new ArrayList<>();

        int start = intervals[0][0];
        int end = intervals[0][1];

        for (int i = 1; i < intervals.length; i++) {
            int currentStart = intervals[i][0];
            int currentEnd = intervals[i][1];

            if (currentStart <= end) {
                end = Math.max(end, currentEnd);
            } else {
                merged.add(new int[]{start, end});
                start = currentStart;
                end = currentEnd;
            }
        }
        merged.add(new int[]{start, end});

        return merged.toArray(new int[merged.size()][]);
    }
}
```

- 时间复杂度：O(n log n)，主要来自排序；遍历为 O(n)。
- 空间复杂度：结果数组为 O(n)；若不计输出，额外空间取决于排序实现和结果暂存，面试中通常说明为 O(n)，排序栈可能为 O(log n)。
- 使用 `Integer.compare`，避免直接相减导致整数溢出。

## 十二、评测与开发实践

### 58. 如何设计 Agent 系统的评测过程？

Agent 评测要同时看**最终结果、执行轨迹、系统性能和安全性**，不能只用一个 LLM Judge 打分。

**1. 定义目标与失败分类**

先明确任务成功：答案正确、文件修改正确、测试通过、没有越权、成本在预算内。建立错误 taxonomy，例如规划错误、工具选错、参数错、检索漏召回、执行失败、未停止、幻觉、越权。

**2. 构建分层数据集**

- 单元集：单个工具选择、参数生成、检索、结构化输出。
- 轨迹集：多步任务，包含合理的中间状态和失败恢复。
- 端到端集：来自真实业务的完整任务和验收环境。
- 安全/对抗集：Prompt Injection、敏感数据、越权工具、重复调用、恶意文件。
- 回归集：每个线上 Bug 都转成长期测试案例。

数据要覆盖常见、长尾、边界和不可完成任务，划分开发集与盲测集，防止 Prompt 对测试集过拟合。

**3. 设计指标**

- 最终结果：Task Success Rate、测试通过率、答案正确率、人工接受率。
- 检索：Recall@K、MRR/nDCG、context precision。
- 工具：选择准确率、参数准确率、调用成功率、无效/重复调用率。
- 轨迹：步骤效率、恢复成功率、是否满足约束、是否在完成后正确停止。
- 系统：P50/P95 延迟、token、费用、吞吐、错误率。
- 安全：越权率、敏感信息泄漏率、高风险动作拦截率。

**4. 评判方法**

能用确定性验证就不用主观判断：代码跑测试、SQL 对结果、JSON 做 schema、引用做匹配。开放文本再使用人工 rubric 或 LLM-as-a-Judge；Judge 要校准、盲评、交换答案顺序，并与人工一致性抽检。

**5. 运行与分析**

固定模型和 Prompt 版本，多次运行处理非确定性；新版本与基线做配对比较，按任务类型切片，而不是只看平均分。失败时查看 trace，定位是哪一层退化。

**6. 上线闭环**

先 shadow/canary，再逐步放量；监控任务成功率、人工接管、成本和安全告警。收集用户反馈和失败轨迹，脱敏后进入回归集。评测本质是持续工程，而不是上线前跑一次 benchmark。

### 59. 使用 AI 编程工具（如 Codex）完成需求的完整流程

可以按下面的闭环来讲：

1. **明确需求与验收标准**：把目标、范围、非目标、兼容性、异常场景和“怎样算完成”说清楚。信息不足时先让工具只读项目，再问真正阻塞的问题。
2. **建立环境认知**：读取项目说明、开发规范和相关文档；检查仓库状态，识别用户已有改动；定位入口、调用链、测试和构建命令。
3. **形成计划**：将需求拆成可验证步骤，指出涉及文件、风险和测试策略。小修改可直接做，跨模块或高风险改动先确认方案。
4. **隔离与保护**：必要时使用分支/worktree；遵循最小权限，安装依赖、联网、删除、部署等动作按需审批，不把密钥写进代码或日志。
5. **增量实现**：先补测试或最小复现，再做小而聚焦的补丁；复用现有抽象和风格，不顺手重构无关模块；每一步都检查真实文件状态。
6. **持续验证**：先跑针对性单测，再跑类型检查、lint、集成测试和必要的 UI/端到端验证。失败后根据错误定位根因，不机械重复同一命令。
7. **审查变更**：查看 diff，确认没有调试代码、生成文件、无关格式化、敏感信息和 API 破坏；检查边界条件、安全和性能风险。
8. **交付说明**：总结改了什么、为什么这样改、验证了什么、哪些未验证及残余风险；给出清晰文件引用和后续操作。需要提交或创建 PR 时，先遵守团队流程。
9. **沉淀反馈**：评审或线上发现的问题加入测试、项目规范或可复用 Skill，形成下一次更可靠的闭环。

这个流程的重点不是“让 AI 一次生成很多代码”，而是让它像工程协作者一样：先理解代码库，做聚焦修改，运行检查，审查差异，并用证据证明完成。OpenAI 官方对 Codex 的典型工作定位也覆盖理解代码库、实现和修复、测试、审查并准备交付。[OpenAI Developers](https://developers.openai.com/)

## 面试使用建议

- 先用 30～60 秒讲结论，再根据追问展开，不要一上来把所有点背完。
- 多用自己项目中的具体例子：数据量、失败案例、指标、权衡和最终结果。
- 遇到“如何优化”类问题，先说要建立基线和分层定位，再谈具体技术，避免堆名词。
- 对 MCP、Memory、RAG 这类概念，最好同时说清“它不是什么”和失败边界。
- 涉及个人经验时只讲真实做过的内容；面试官往往会继续追问 schema、指标、日志和异常处理。
